"OpenAI/Codex encrypt prompts sent to subagents. Have to assume this is meant to prevent distillation" - Theo rediscovers a 3-month-old change, and the motive question is live again

September 9, 2026, ~7:50 PM IST · Theo's post is ~14h old (6:02 AM IST): 99.4K views / 1.2K likes / 76 replies at capture · the underlying change shipped June 5 and HN fought over it July 14 (425 points, 249 comments) · blow-up: medium (a big dev-creator reframing an old change as a distillation moat, with fresh technical details in the replies)
The gistTheo (t3.gg, 400K+ followers, runs the T3 Code agent harness) noticed that OpenAI's Codex CLI encrypts the prompts a parent agent sends to its subagents, and inferred the motive: "Have to assume this is meant to prevent distillation." (Distillation = training a cheaper model on a stronger model's outputs; if you can't read the task prompts, you can't easily harvest them.) The catch: this is not new. OpenAI merged the change on June 5 (PR #26210) and Hacker News spent 249 comments on it in mid-July - mostly framing it as an auditability regression (you can no longer see what your own agents told each other), not a distillation story. What IS new in today's thread: claims that the encryption was recently decrypted, that it uses "fernet" (a symmetric scheme - same key locks and unlocks, so a client-side key would be readable), and that the task name still sits in plaintext next to the encrypted blob. The live question: anti-distillation moat, security design, or just a closed-source move inside an "open source" CLI?

What happened

At 6:02 AM IST, Theo posted a screenshot of Codex's subagent traffic showing encrypted prompt payloads: "Today I learned that OpenAI/Codex encrypt prompts sent to subagents. Have to assume this is meant to prevent distillation." 99.4K views and 76 replies in ~14 hours - modest by Theo standards, but the replies are technical, not cheerleading.

The replies split into three camps: motive-confirmers adding evidence (it was recently decrypted; the scheme is fernet; task names stay plaintext), motive-skeptics (why encrypt between your own systems? does it even work?), and practitioners routing around it (shell out to subagents in both harnesses and read prompts freely).

How we got here

  1. June 5, 2026: the change ships quietly. OpenAI merged PR #26210, "Encrypt multi-agent v2 message payloads", into the open-source Codex CLI. The commit message states the problem plainly: parent-agent task text used to flow as plaintext through tool arguments, get persisted in history/rollouts, and arrive as ordinary JSON. After the PR, every spawn_agent call's task description is ciphertext. Affects MultiAgentV2 builds after CLI 0.137.0.
  2. July 14: the press wave and the HN fight. TemperatureZero ("Codex Encrypted Its Sub-Agent Tasks. Only OpenAI Has the Key.") and Developers Digest (coverage) traced the change to #26210; terminalblog (July 17) confirmed that on GPT-5.6-Sol and GPT-5.6-Terra, as of CLI 0.144.4, the delegation instruction is ciphertext "and only OpenAI holds the key." HN's thread (48905028) hit 425 points - and spent its first dozen comments untangling a misleading title (no, inference is not done on ciphertext; the ciphertext is just what the user can see).
  3. The open issues are the paper trail. GitHub issues #28058 ("encrypted MultiAgentV2 messages remove readable task audit trail"), #32753 ("subagent instructions are no longer observable"), and #37822 (the encrypted payload getting dropped entirely - subagent never receives its task) document the cost: operators cannot inspect what their own agents instructed each other to do.
  4. Sep 9, 6:02 AM IST: Theo rediscovers it, with a motive attached. The July framing was "auditability regression." Theo's framing is "distillation defense" - a competitive-moat story, not an ops story. That reframe is what the 76 replies are actually litigating.

What's new today (monitoring)

  1. Claim: it was recently decrypted. Reply account Data Sculpting Inc. asserts "This was decrypted recently. It obviously has only 1 purpose: tripping up distillation... The decryption & re-encryption could allow exploit vectors." Unverified - no link to the claimed decryption work - but if true it defuses the moat reading entirely.
  2. Claim: the scheme is fernet. Reply account alexhristov: "Its using fernet." Fernet is a symmetric scheme (AES-128 with an integrity check) where one key both locks and unlocks. If the key ships in the open-source client, the encryption hides prompts from casual log readers, not from anyone motivated. That would make it a speed bump, not a vault - which weakens Theo's distillation reading and strengthens the "stop proxy resellers / casual harvesting" reading.
  3. The task name stays plaintext. Elledyne Labs: "encryption for subagent prompts but the task name sitting right next to it in plaintext is wild. if distillation is the worry, what's actually stopping someone from reading the wrapper traffic around the encrypted blob?" The metadata leak is the strongest concrete detail in the thread.
  4. The practitioner workaround is trivial. Lando (fragileLando): shelling out to subagents "in both directions to use the appropriate models in their native harness still goes hard, and can see prompts no worries." If the harness you control can route around it, the control is aimed at harvesters, not users.
  5. Watch for an OpenAI response. None so far. The July wave also passed without an official motive statement - the commit message (plaintext "persisted in history/rollouts") is the only on-record rationale, and it reads like a data-hygiene fix, not an anti-distillation measure.

The argument map

  • Claim A (Theo's): the encryption exists to prevent distillation - stop others harvesting parent-to-subagent task prompts as training data. Support: labs are paranoid about distillation in a race year; HN's londons_explore independently guessed the same motive in July ("frustrate efforts to proxy large numbers of user requests and responses and use it to train competitor models"). Counter: fernet + client-side key + plaintext task names = a harvester decrypts in an afternoon; real anti-distillation would happen server-side.
  • Claim B (July HN's): this is an auditability regression - you can no longer inspect what your own agents told each other. Support: three open GitHub issues, all unanswered with a fix; #37822 shows the encryption path actively breaking task delivery. Counter: the plaintext was being persisted into rollouts - a data-hygiene problem worth fixing.
  • Claim C (the trust joke that isn't a joke): Chahat Sharma - "does this mean they don't fully trust their own subagents lol because why else would you encrypt between your own systems." The encryption happens on the wire between orchestrator and subagent, which is odd unless the threat model includes the user's own logs.
  • Claim D (the open-source question): HN's pradeep1177 - "Then why to even keep codex open source?" If the interesting orchestration behavior is encrypted and key-controlled by OpenAI, the CLI's open-source-ness is increasingly a UI shell.

The key facts, dissected

  1. What exactly is encrypted. The task prompt payload a parent agent sends when spawning or messaging a subagent in MultiAgentV2 (spawn_agent, send_message paths). Not inference, not the model weights, not the user's own typed prompts. (commit 5f4d06e)
  2. Who holds the key. Per terminalblog's July testing on GPT-5.6-Sol/Terra (CLI 0.144.4), the ciphertext is not locally decryptable through any exposed mechanism - "only OpenAI holds the key." If today's "fernet" claim is accurate, the key must live somewhere the client can reach; those two reports are in tension, and the resolution (key in binary? server-side unwrap?) is the real story. This is the fact a good reply would nail down before taking a side.
  3. The stated reason vs the inferred reason. The commit message says plaintext task text was being persisted into history/rollouts - a data-hygiene framing. No OpenAI statement mentions distillation. The distillation motive is inference by Theo and londons_explore, plausible, unconfirmed.
  4. The blast radius is real either way. Three open issues document operators losing the ability to audit multi-agent runs, and one (#37822) documents the encrypted payload being dropped so the subagent never receives its task. Whatever the motive, the feature shipped with an observability cost and at least one correctness bug.
  5. Timing. Shipped June 5, press July 14, rediscovered by Theo Sep 9. The three-month gap means the "news" here is the frame, not the change - which is exactly why the thread is about motives.

Both sides

"It's a distillation moat" (Theo's read)

Steelman

Frontier labs in a race year are visibly paranoid about capability leakage - the same OpenAI that publishes Navier-Stokes receipts to preempt scooping also knows that multi-agent orchestration traces are premium training data. Parent-to-subagent prompts encode decomposition strategy, which is the part competitors can't easily generate. Encrypting the one channel that leaks it, accepting an auditability regression as collateral, and saying nothing is exactly what a quiet moat looks like. HN's gray-market field report (reseller proxies dying overnight) shows OpenAI will take real user pain to close harvesting channels.

Strawman

"OpenAI is terrified and encrypting everything" - except the scheme is reportedly fernet with a client-reachable key, the task names sit in plaintext, anyone routing through their own harness sees everything, and it was allegedly decrypted weeks ago. If this is a moat, it's a moat you can step over.

"It's data hygiene + an auditability regression" (July HN's read)

Steelman

Read the commit message: plaintext task text was being persisted into history files and rollouts - meaning every user's orchestration internals were landing on disk in the clear, scrapable by any local process and syncable by accident. Encrypting persisted inter-agent messages is boring security hygiene. The actual scandal is the execution: no operator decryption path, three unanswered issues, and a bug where the subagent never receives its task. This is a rushed closed-door change inside an open-source shell, not a conspiracy.

Strawman

"It's just hygiene, nothing to see" - except hygiene doesn't require withholding the key from the operator whose machine the agents run on. A hygienic design encrypts at rest with a user-held key. This design makes OpenAI the sole reader of your agents' instructions, which is a strange shape for a feature with no strategic purpose.
